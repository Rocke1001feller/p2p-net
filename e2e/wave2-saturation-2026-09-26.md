> 对应 `docs/cost-model.md` §6.4 待标定清单第 1 条（单机饱和压测）。

> 软件层（relay/caddy/host 桌腿/driver）在 ~580 并发隧道连接下各项水位均远离上限，连接数天花板本次未触达。**

## 0. 实验设置与干扰源登记

- 链路：driver（Mac，node）→ `wss://49.233.155.13/tunnel/s/<deviceId>/s/8888/echo` → caddy(443) → relay(127.0.0.1:19700) → Mac host 隧道腿 → `127.0.0.1:8888` echo（白名单内端口）。
- 压测工具：`scripts/bench/tunnel-saturation.mjs`（W2-3 driver，eb08c3b 合入）；每轮 `ulimit -n 65536` 钉死。
- 双侧采样：driver 自报（仅供对账）＋ VPS 侧 15–20s 采样器（top/ss/eth0 计数器/procs）＋ Mac host 腿 10–15s 采样器（lsof 计数/CPU/RSS）。
- 干扰源登记（诚实清单）：
  1. 压测与真机共用生产 relay——每轮 <2min，轮间确认恢复（`p2p-net status` 隧道腿 1/1、本地连接回落基线 8）；
  2. 3000 档在 1000d 结束后 ~85s 起跑，管道余量未完全回落，该轮 openP95 受污染（见 §2 表注）；
  3. coturn 公网扫描器背景税常驻（e2e/compression-ab-results-2026-09-24.md 已量化）；
  4. 各轮均未进稳态——饱和判据（新建成功率 <0.95）在爬坡期触发即停，这是判据设计行为，非异常；
  5. driver 与 host 同机（Mac Intel x86_64），driver 侧 TLS 握手 CPU 实测 <0.5 核，非瓶颈。

### 2.3 出口带宽独立实测（排除压测自证）

`ssh cat /dev/zero 文件 48MB` 单流实测 VPS→Mac：**143.7s ⇒ 2.67 Mbps**。

## 3. 机制分析（为什么失败形态是「排队超时」）

1. 每新建 1 条隧道 WS 连接的 TLS 握手字节（VPS→driver 证书链等）实测 ≈ **9.1 KB/conn**（1000c 轮 VPS tx 增量 9.12MB ÷ 1000）。
2. 100/s 爬坡 ⇒ 握手字节需求 9.1KB×100/s ≈ **7.3 Mbps ≫ 3 Mbps** → 握手排队，driver 侧 open 超时（~10s 量级）批量失败。观察建连吞吐 ≈ 26–60/s，与「9.1KB/conn × R ≤ 3Mbps ⇒ R ≤ ~40/s」的算术一致。
3. 20/s 爬坡（run4）握手需求 ≈1.5 Mbps < 3 Mbps → 建连基本成功（openP95 1.68s，ok=586）；随后心跳+大响应流量起来，管道打满（rx 7.66/tx 3.57 Mbps）→ 大响应 0/28 完成、心跳 432 失败。**失败起点与 eth0 贴顶时刻精确重合。**
4. relay 转发面（`src/tunnel/relay.ts`）与 host 桥（`src/bridge/ws.ts`）均为全异步无串行点（代码走查），与「CPU/fd 无压力、纯带宽排队」的实测形态互相印证。

## 4. 结论（→ cost-model §6.1）

1. **单 VPS 并发上限 = 带宽约束，不是连接数约束**（本档硬件）。活跃会话上限 ≈ 出口带宽 ÷ 会话均速：
   3 Mbps ÷ 50 kbps ≈ **60 个活跃中继会话**（30 Mbps 档同算术 ≈ 600 个）。
2. **静默/轻载在线连接数 ≥582 实测无软件压力**（fd 671、host CPU<6%、VPS CPU 93% idle）；连接数维度天花板本次未触达——
   「静默连接积压上限」属另一实验（全静默爬坡，不带心跳/大响应），本波不做，登记待办。
3. **TLS 建连吞吐 ≈ 26–60/s**（受握手字节×带宽约束；该值随带宽档线性放大）。
4. 对 10 万用户目标：成本与扩容规划必须**以带宽（和流量）为第一变量**——直连率/隧道率决定账单，连接数不构成小 VPS 的容量约束。
5. 运维含义：压测/重连风暴场景下的用户体验退化（open 超时、心跳失败）本质是管道排队——
   客户端重试必须带退避（已有），且监控应把 **eth0 tx 贴顶** 作为首要饱和信号（先于一切进程内指标）。
