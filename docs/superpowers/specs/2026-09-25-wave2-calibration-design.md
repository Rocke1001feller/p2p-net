# Wave 2 设计：标定清单与直连率杠杆（v0.3.x）

日期：2026-09-25 ｜ 状态：已获方向批准（用户裁决：Wave 2 标定清单，解决生死约束；版本线 v0.3.x）
上游依据：`docs/cost-model.md` §6.4 待标定清单；Wave 1 spec §2.2/§D9 三支柱分工；主仓 `docs/first-live-run-report.md`「中继=暖场通道」产品级认知。

## 0. 北极星对齐（为什么是这个 Wave）

北极星：10 万+ 用户、几乎免费、零配置。成本方程 `VPS 成本 = 在线数 ×（中继率+隧道率）× 会话带宽 × 字节因子` 中，字节因子已【实测-本仓】（1.27），**中继率是剩余最大未知数**（外部 2/3~100%，本仓 N=1 且曾误判）；直连率每降一档，账单翻数倍。Wave 2 = 把未知数变成【实测-本仓】，并建成提升直连率的第一个工程杠杆。

- 量化锚（沿用 D9）：单位成本 ≤¥4/在线·月；10 万注册/10% 并发给出 VPS 配置清单与账单区间。
- 底线：任何改动不得压破 v0.1.0 四指标基线（真机回归门禁）。
- 全局约束（沿用 Wave 1 §4）：简单鲁棒，严控复杂度；二期不做 ws 信令长连、不做决策引擎。

## 1. 范围（In / Out）

**In**（§6.4 五项全收）：
1. 单机饱和压测（v3 方法论）
2. 蜂窝×家宽×运营商直连率矩阵 N≥20
3. NAT 类型 facts
4. 级联顺序成本复审
5. 「暖场通道」relay→direct 后台升级轮

**Out**：ws 信令长连（三期）、Windows 服务化（ROADMAP 二期项）、B 类 Pages 入口、多 Server 聚合 UI。

## 2. 方案权衡（三选一，已定）

- **方案一·严格串行**（仪器→标定→杠杆）：最稳最慢，杠杆见效最晚。弃。
- **方案二·双轨并行（选定）**：仪器轨（T1 分桶计量、T2 NAT facts）先行 → 标定轨（T3 矩阵战役、T4 饱和压测、T5 级联复审）与杠杆 spike（T6）并行展开；T6 实现排在仪器就位后（收益评估依赖 T1 分桶）。理由：T6 spike 是独立技术问题不依赖矩阵结果；并行不牺牲证据纪律。
- **方案三·杠杆优先**：先赌升级轮后补基线——无基线则收益不可评估，违反证据先行。弃。

## 3. 任务分解（6 任务 / 3 轨）

### 仪器轨

**T1 分桶计量**：events.jsonl 与 `/status` 增补 `pathType × 接入类型` 分桶。接入类型来源：PWA 侧 Network Information API 粗分（cellular/wifi）+ 配对元数据手标运营商（电信/联通/其他），host 侧会话元数据落盘。语料 parity 同步更新（机制甲3 纪律）。
- 复杂度：小（<200 行净增）。门禁：parity 66+ 全绿。

**T2 NAT facts 探针**：RFC 5780 简化版（mapping：endpoint-independent?；filtering：addr/port-restricted?；hairpin），探测经**自建 coturn**（外部公共 STUN 国内不可靠——constants.ts 既有裁决）。host 侧入 `doctor` 新层；浏览器侧经根包 `./browser` 导出供 PWA 在 connect 时随会话上报，facts 入 events.jsonl。
- 复杂度：中（探测状态机 + 双侧暴露）。门禁：探测结果可复现（同网两次同结论）。

### 标定轨（依赖 T1/T2 就位，彼此并行）

**T3 直连率矩阵战役 N≥20**：矩阵 = {电信蜂窝, 联通蜂窝} × {家宽, 办公网} × 时段；资产 = Android/电信 + iPhone/联通 + Mac/家宽。每组合 N≥20 会话，pathType 分桶统计。产物：e2e/ 矩阵报告 + cost-model §6.1 中继率行刷新为【实测-本仓 N≥20】（带置信区间，禁止点估计外推）。
- 性质：ops 战役 + 分析，代码零净增（用 T1/T2 仪器）。

**T4 单机饱和压测**：搬 v3 方法论——并发真值=服务端采样（`/status` + VPS vnstat，不信 driver 自报）；爬坡 ≈200 连接/s；TLS 建连吞吐第一约束单独成档。靶面：隧道腿（WS 经 caddy）为主、TURN allocation 为辅。driver 为 Node 开发侧脚本（放 `scripts/bench/`，不进 npm 主依赖）。已知局限如实记录：单机 driver 受端口/文件描述符限制（v3 实录 ~2k 端口耗尽），用 127/8 多源地址部分缓解并在报告中标注口径。产物：饱和曲线（并发 vs 吞吐/时延/错误率）+ TLS 建连吞吐 + 单 VPS 并发上限入档 cost-model。
- 复杂度：中（driver 新建，被测零改动）。

**T5 级联顺序成本复审**：现序实证已是 `p2p→tunnel→turn`（cascadePlan.ts:11；Wave 1 spec 中「v0.1.0 现状 TURN 先于隧道」已过时）。复审 = 本仓实测建链时延（tunnel vs TURN 各 N≥10）+ 字节因子复核（隧道 1.17-1.20 vs TURN 1.27 已近持平）→ 裁决入档 cost-model + cascadePlan 注释更新。纯分析小活。

### 杠杆轨

**T6 暖场升级轮（relay→direct 后台升级）——spike 先行**：
- 问题：WebRTC 建连期 ICE 定型，无运行时升级机制（EasyTier 有，WebRTC 无），需自研。
- 路线 a：ICE restart——浏览器原生 `createOffer({iceRestart:true})`；werift 0.24.4 侧支持未知（源码未见 restartIce，spike 第一问）。
- 路线 b：影子 PC——relay 会话不动，后台建 p2p-only 新 PC，直连成功原子切换数据面，失败静默丢弃（现网零风险，代价是双 PC 瞬时内存）。
- spike 判定：werift ICE restart 可行性 + 浏览器端 restart 后 nominated 对迁移行为实测。**spike 报告获批后才进实现**；实现形态预算：独立模块 `upgradeWheel.ts` + 协议帧 1 种 + 门控开关（默认开、可关，灰度经真机门禁）。这是 Wave 2 唯一允许可观复杂度的点，其余一律从简。

## 4. 顺序与依赖

```
T1 → T2 → ┬ T3（矩阵战役，需双真机在场，用户配合窗口）
          ├ T4（饱和压测，本机+VPS 即可）
          ├ T5（纯分析，随时）
          └ T6 spike → 报告 → 实现（实现需 T1 分桶计量评估收益）
```

## 5. Wave 2 门禁（Go/No-Go，发布 v0.3.0 前全过）

1. cost-model §6.1 参数表：中继率、单 VPS 并发上限、TLS 建连吞吐、级联裁决全部刷新为【实测-本仓】并带误差带。
2. 真机四指标回归不破 v0.1.0 基线（双机：Android/电信 + iPhone/联通）。
3. 全量测试链绿（lint:twins → parallel → serial → parity），新增测试遵守动态端口纪律。
4. 门禁报告归档 e2e/；T6 若进实现，须有专项 A/B（升级成功率、切换中断时长、回退率）。

## 6. 风险与诚实清单

- T4 单 driver 端口天花板：标定的是 VPS 侧饱和点，driver 侧瓶颈须分离陈述（历史教训：两症状可分离必分离）。
- T3 的 N≥20 样本依赖真实网络多样性；两手机×两网络能覆盖的象限有限，覆盖不到的象限在报告中留白而非编造。
- T6 路线 b 的双 PC 内存开销在低端手机未实测——spike 报告须含低端机数据。
- LE IP 证书 6 天续期（coturn-relay-ops §8.4 遗留）：饱和压测期间若撞上续期窗口，须把证书事件计入干扰源。
