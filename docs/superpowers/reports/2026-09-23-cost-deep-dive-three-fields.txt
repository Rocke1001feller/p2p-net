**饱和点（什么先崩）**：
1. **2C/1.9G 机 ≈4.1k 并发在线**（【实测】峰值 4113；「吃满它的是 TLS 握手吞吐、不是消息面」=【推断】——RSS 114-122MB、load ≤0.2 只支持"不是消息面"那一半）。2C 上 TLS 建连吞吐实测 ~60/s（1k 档）→ ~17/s（10k 档突发）（`signaling-load-relay-sh-2026-09-14.md:209-222`）；「吞吐随核数近似线性」=【推断】（无 4C 对照）。
2. **4C/7.6G 机 10000 是目标值不是天花板**——">10000 未测，真正的容量上限需递增档位（12500/15000/20000）"（`signaling-10000-rerun-2026-09-17.md:79`）。
3. **先崩的从来不是消息面而是"建连面 + 心跳语义"**：修复前心跳「一拍未回 pong（5s 窗）即 terminate」在 WAN 拥塞窗口批量收割健康连接——6k 档 opened→alive 只有 11.8%；对照实验钉死（100 条空闲 90s 零死亡 vs 事件循环失速 12s 后 ~8s 内 100/100 被割、close code 全 1006）（`signaling-load-relay-sh-2026-09-14.md:101-140`）。修复 = `deadAfterMs` 默认 15000（=3×heartbeatMs）+ 任意入站帧刷新存活（`packages/node/src/signaling/relay-server.ts:96-98,241-252`）。
4. **driver 侧瓶颈形状**（压测方法论关键）：Mac 单机 ~2k 后源端口池耗尽（EADDRNOTAVAIL）、~6k 并发会话时路径崩溃性丢流（采样 SSH 与全部 ws 同一时刻被 RST）（`signaling-load-relay-sh-2026-09-14.md:180-201`）。

**每连接内存**：
- driver 侧：Mac `1k 168.6MB → 5k ~520MB → 10k 741.9MB`（`signaling-load-relay-sh-2026-09-14.md:99`）；云 driver `bj2 243MB@2428 连接、sg 367MB@2276`；门禁档 `315MB@3500 / 328MB@3000 / 272MB@2500 / 174MB@1000`（`signaling-gate-sh2-2026-09-14.md:33-38`）；9-17 复测 `rssPeakMB 242.7 / 318.3 @2500`（`bench/runs/signaling-10000-2026-09-17/run2.json`）。**定容规则 ≈1GB 可用内存 / 1000 连接**（【推断】，依据强度 n=1——`signaling-load-relay-sh-2026-09-14.md:356-361`）。换算 ≈ **100-150 KB/连接**（Node ws 客户端侧）。
- 服务端：2C 机 4113 并发时 RSS 仅 114-122MB（≈ **28 B/连接 级**，ws 服务端极轻）；4C/7.6G 机万级时 heap 上限 6144MB、稳态可用内存 ≥6.3GB。healthz 自带 `rssMB` 字段（`packages/node/launcher/signaling-relay.mjs:77`）。

**断连率随规模的形状**：死亡**聚簇在建连拥塞窗口**（爬升期），不是均匀分布——"幸存的 31 条连接在拥塞结束后稳定存活 28s+ 零死亡"（`signaling-load-relay-sh-2026-09-14.md:122-124`）。修复后形状变成：爬升→稳态 100% → 阶梯下降（driver 按 slice 退出的预期行为）。run1 唯一的 1/10000 `closedAfterOpen` 成因【未验证】（无 terminate 留痕）。

### D. 真机 field acceptance（2026-09-17，4 发射端 × 3 通道 × PWA/Flutter 双侧，真实蜂窝）

`docs/field-acceptance/2026-09-17-full-matrix-and-baseline.md`：

- **P2P 直连占比本轮 ≈0【实测】**：所有 p2p 档 facts 显示 `whyNotCheaper.p2p: "选定候选对为 relay（直连候选对 2 条未成功）"`——"蜂窝+家庭 NAT 双向打洞成功率本就低（v2 时代实测 1/3）【推断】；P2P 直连占比（GA ≥75%）远未达标——这直接关系到中继带宽成本"（`:144-151`）

### E. werift 同意黑洞（对应 p2p-net "stall/~周期死亡" 的同族缺陷）

issue #69 根因【实测】：werift 0.24.4 的 RFC 7675 同意检查**每 4-6s 单发无重传**，连续 30s 无响应 → `consentFresh=false` + `state=failed` + **循环自己退出且无自愈路径**；之后 `IceTransport.send()` 首行静默 return（不抛错、不计数、不打日志）→ SCTP 收不到 SACK → `dc.bufferedAmount` 永久钉在背压阈值上 = 假健康黑洞。公网现场：同一会话 Mac 侧同意死亡 13 次、每 ≈30s 复发。修复 = 看门狗就地 `setState('connected') + queryConsent()` 复活（默认 3s 周期、上限 5 次）——`packages/node/src/transport/consent-watchdog.ts:1-39,98-124`、`docs/benchmark/upload-stall-69-2026-09-16.md:8-34,186-222`。**注意该缺陷每侧各自独立，必须双侧都装看门狗**（`upload-stall-69:93-96`）。

## ② werift ^0.24.4 下判定直连 vs 中继的实证 API

**结论：可用，且该仓已在生产代码 + 真机测量中真跑。【实测】级证据链如下。**

1. **API 入口**：`RTCPeerConnection.getStats()`（`node_modules/werift/lib/webrtc/src/peerConnection.js:1021`），返回 `RTCStatsReport`（Map 子类，`.values()` 展平成行）。
2. **行形状（安装包源码实证，werift 0.24.4，`node_modules/werift/package.json:3`）**：
   - candidate-pair 行构造于 `node_modules/werift/lib/webrtc/src/transport/ice.js:355-380`：`{type:'candidate-pair', id, localCandidateId, remoteCandidateId, state, nominated, packetsSent/Received, bytesSent, bytesReceived, currentRoundTripTime, …, consentRequestsSent}`——**没有 `selected` 字段**；state 枚举 = frozen/waiting/in-progress/**succeeded**/failed（同文件 `:13-28`）；pairs 输出时 nominated 排前（`:349-353`）。
   - local/remote-candidate 行：`{type, id, address, port, protocol, candidateType, priority, foundation, relatedAddress, relatedPort, usernameFragment, tcpType}`（`ice.js:310-345`）——`candidateType ∈ host/srflx/prflx/relay`。
3. **判定代码（仓内现成实现，可直接移植）**：
   - 选定对判据：`type==='candidate-pair' && (selected===true || state==='succeeded')`——"werift 0.24.4 的 candidate-pair 行没有 selected 字段，选定对用 state==='succeeded'（nominated 亦在）；浏览器侧是 selected===true 语法。两判据都写，state 为主——双侧通吃"（`packages/core/src/status.ts:1-14`）
   - 路径类型：`local?.candidateType ?? remote?.candidateType`；`relay→'relay'`，`host/srflx→'p2p'`（`status.ts:16-25`）；含 prflx 的更全枚举在 `packages/core/src/facts.ts:445-456`（`pairCandidateTypeFromStats`）
   - 字节账本：`pairBytesFromStats` 读选定对 `bytesSent/bytesReceived` 累计值做增量（`facts.ts:430-437`）——**这正是 p2p-net "帧账本加路径类型测量"要的实证 API**，T-C 成本报告里的 TURN 1.680 因子就是这么量出来的（`tc-cost-2026-09-15.md:50-57`）
   - 采样节拍：host 侧 5s 定时 `refreshStats()`（`packages/node/src/peer.ts:84,285-306`），产出 `PeerStatsReading{pairType, candidateType, rttMs, relayAddr, bytes, evidence}`（`peer.ts:86-98`）；快照路径禁 I/O，只读缓存
   - 证据汇总：`icePairEvidence`（total/failed/direct/relay/unknown 候选对计数，ICE 失败细分归因用）（`facts.ts:458-480`）
4. **运行时实证等级**：集成测试用真实 werift PC 全链跑（`packages/node/tests/host.integration.test.ts:5-6` import 真实 `DvaHostAgent/DvaPeer`，`newPc()` 构造真实 `RTCPeerConnection`，`peer.ts:127-134`）；真机/T-C 测量里 host 侧 107 次 `connected` 均报 `pairType:p2p`（`tc-b-experiment-2026-09-15.md:140`）；field 验收里 facts 的 `whyNotCheaper.p2p:"选定候选对为 relay…"` 也是这条链路的产出。**「无 selected 字段」这一原始取证出自 v2 仓 gate4 spike（`packages/core/src/status.ts:4` 引 `examples/gate4/README.md`），该目录在本机 v3 cores 副本中不存在——原始 artifact 未亲见，但安装包源码（本条 2）独立证实了同一事实。**
5. **浏览器/Flutter 侧差异**：浏览器原生 stats 用 `selected===true`（`packages/browser/src/webrtc-session.ts:20,219`）；Flutter 经 `flutter_webrtc` 展平后同判据（`packages/flutter_core/lib/src/status.dart:25-45`）。p2p-net 的 host 在 Node/werift 侧 → 用 `state==='succeeded'`；PWA 侧 → `selected`。

## ① TURN 字节因子 1.68：测量方法与账务口径【实测】

**对照组怎么搭**（tc-cost:6）：host = relay-sh2（腾讯云上海 4C/7.6G），peer = 操作机 Mac（家宽 NAT），TURN 服务器 = relay-sh（火山 5 Mbps 档）。载荷 = **3 轮 × 32 MiB × 2 方向 = 201 326 592 B**（tc-cost:52），双向各 3 有效轮，CV 1.3%/5.6%（tc-cost:31）。三批独立采集（22:10 / 22:47 / 23:10）读数一致（0.30–0.34 MiB/s），"可复现性最好"（tc-cost:39-40）。

**算了哪些字节**（tc-cost:48-57 + `tc-accounting.ts:39-53,69-89`）：
- peer 腿 = `getStats` **选定候选对字节增量**（wire 字节，含 DTLS/SCTP/UDP 封装）；tunnel 无 getStats 用 HTTP body 近似（低估 ~1%）；
- desktop 腿 = host 侧帧计数（JSON 串长）；TURN 的 host 腿"按对称计"——`tc-accounting.ts:129-141`：「peer 腿实测 rx≈D·w、tx≈U·w，故双腿总 egress = tx+rx」；
- tx/rx 分开、app/wire 分开，"每个因子都有名有姓"（tc-accounting.ts:4-6）。

**1.68 的原始账**（artifact `bench/runs/tc-2026091514595-8307b9-T-C-turn.json` 的 `raw.cost.account`，我用 python 复核）：peerLegTx=175 061 319、peerLegRx=163 136 005，(tx+rx)/payload = **1.6798442800839741**（tc-cost:63 同数）。

**账务口径**：
- 单价 **0.8 元/GB**（`tc-accounting.ts:17-18`）；三口径并列：①单向（egress）②双向（ingress+egress）③固定带宽折算（tc-cost:75-76）。
- 成本表（tc-cost:80-84）：TURN 单向 **1.344** / 双向 2.688；隧道 prod 单向 **0.933** / 双向 1.890；隧道 rig 0.400；P2P = 0。「成本决策用 prod 列」（tc-cost:90）。
- **rig vs prod 双列**：rig=采集拓扑（desktop 与 relay 同机走回环），prod=生产外推（两腿都出公网 NIC）；「隧道省的是公网腿，省不掉 desktop 腿」——隧道 prod 是 rig 的 2.3 倍（tc-cost:86-89）。
- 固定带宽口径（tc-cost:94-110 + `tc-accounting.ts:209-233`）：月出公网 = 带宽 × 31557600/12 s × u；**5 Mbps 档 u=50% → 0.8 TB/月**；盈亏平衡「**每 100 元月租换 125 GB/月**」；「5 Mbps 档节点月供载荷能力 ≈ 0.8 TB ÷ 1.68 ≈ **0.48 TB**（u=50% 计）」。
- **采集器缺陷留痕**（tc-cost:68-71）：旧版隧道腿双重计数曾把成本序打成"贴脸"（1.333 vs 1.344），修正后 prod 因子 1.196/1.167——教训：字节账的计数器本身要做对账实验。
- **#15 的 3.3× 矛盾**：方向口径只贡献 ~2×（两通道都是，tc-cost:114-124），剩余因子候选是日均时长（8h vs 全天 = 3×），**未闭合**，收敛优先级「时长 > 方向 > 通道成分」（tc-cost:160-161）。

| 场景 | 直连率 | 等级 | 位置 |
|---|---|---|---|
| Mac 家宽 + VPN ON（家宽 NAT ↔ 云 host） | **0/5** | 【实测】 | tc-cost:165,29 |
| 干净云机 peer（relay-sh 1:1 NAT）↔ 云 host | **10/10，384 MiB 全对账** | 【实测】 | tc-b:18-21,169-176 |
| 同 Mac，VPN OFF（唯一变量） | **5/5，下行 9.97 MiB/s**（TURN 兜底仅 0.32） | 【实测】 | tc-a:41-52 |

**机制级发现（全是实测）**：
- **失败定因**：VPN 使「单 socket 多目的地 UDP 被钉到首个目标端口/整体丢失」（udp-preflight A/B/C 三组对照，tc-cost:178-194；on/off 18/18 钉流↔18/18 正确，tc-a:32-35）。werift 恰是"单 socket 多目的地"形态（tc-cost:188-190）。
- **云 host 侧**：安全组对**无会话入向 UDP 一律丢弃**（host 侧 50 次 STUN 事务超时），打洞靠 **peer 发起、host 回包**的路径成功（tc-b:30-32,186-190）；云 host 需 `--ice-port-range 50000-50019` 落在放行段（tc-cost:200）。
- **VPN 绕过四方案全部实测有效**（vpn-bypass:24-29）：A1 `IP_BOUND_IF=en0`、A1-node 绑定源地址、A3 每目标独立 socket 均 18/18 恢复；A2 host route 完成端到端判决。落地评估：A1 最优（用户态、随库分发），但跨平台等价物未测（vpn-bypass:96-106,124-127）。
- **IPv6**：仅作为候选之一出现（tc-cost:189），**无专项实验**【未验证】。
- **STUN 配置**：p2p 档只用自建 coturn 做 STUN、不含 TURN 候选（`docs/architecture.md:88`）；「STUN 服务器多样性」只是建议，未做（full-matrix:174）【未验证】。
- **口径警告**：直连占比口径曾三处互斥（按字节/时间加权/按会话数），2026-09-13 定稿**按字节**（`docs/control-spec.md:621`）。目标档：GA ≥75% / COM ≥85% / STR ≥92%（`metrics-baseline.md:197`），行业锚 S13 ~80%、S11 Tailscale >90%（:51,53）。

## ③ TURN 双 transport 实验【实测】

位置：`docs/field-acceptance/2026-09-17-full-matrix-and-baseline.md:86-142`，实体机蜂窝、三臂对照（n=6×3，唯一变量 = transport）：

| 臂 | 配置 | 成功率 |
|---|---|---|
| A | UDP only | **6/6 = 100%** |
| B | TCP only | 5/6 = 83% |
| C | **both（旧生产配置）** | **2/6 = 33%** |

机制（full-matrix:113-116）：「同时下发两个 TURN URL 时，ICE agent 在两条 relay 路径间竞争，导致 TURN allocation 冲突与 15s 超时」；失败时 coturn 记 `allocation timeout` / `stale session state`（:96-99）。修复已落地：`supabase/functions/turn-credentials/index.ts:41-58` 默认只发 `?transport=udp`，修复后验证 **5/6 = 83%**（:131-134）；残留 1/6 归因为**蜂窝多出口 NAT**（同会话两个出口 IP `36.112.201.175`/`106.37.77.38`，运营商侧，:136-139）。

**成本含义**：①both 配置下 2/3 的 TURN 会话连不上 → 重试/降级会放大信令与建链开销；②TCP-only 本就 83% 且 TURN-over-TCP 吞吐更差，UDP 优先是成本与成功率双赢；③TURN 档建链 4158–6738 ms vs 隧道 460–1752 ms（full-matrix:71-73），慢建链本身也是会话成本。

## ④ base64 税（33%）与二进制帧测算【实测发现 + 文档推断测算，未实施】

- 实测：「每 16384 B 应答片编成 21 848 chars（4/3）。**每 1 GB 载荷 = 1.333 GB 上路**；JSON 包装 + DTLS/SCTP/UDP 头把 1.333 抬到 TURN 实测的 **1.680**（1.26×）」（tc-cost:135-141）。隧道 desktop 腿字节账直接可见 4/3：140 102 039 ≈ 96 MiB × 4/3（tc-cost:65-66）。
- 砍掉后的测算【文档推断】：「TURN 单向单位成本：1.344 → 约 1.01 元/载荷 GB（**−25%**）；隧道 desktop 腿：1.167 → 约 0.9（−23%）」（tc-cost:142-146）。落点写明 `packages/core/src/frames.ts`（`chunkB64` 面），「建议单独立项（本批只管测出来）」（tc-cost:148-149）。
- **现状核实**：二进制帧至今未实施——DataChannel 仍发 JSON 字符串（`packages/node/src/bridge/http.ts:120`、`packages/browser/src/webrtc-session.ts:237`、`packages/browser/src/cascade.ts:129` 的 `JSON.stringify(frame)`），`chunkB64`/`dataB64`/`bodyB64` 遍布 core/node/browser 三端。issue-ledger 与 roadmap 无对应已完成项。**这层税原样保留，是 p2p-net 可直接收割的存量。**

## ⑤ 压缩：grep 实证【未验证 = 处女地】

- gzip 的出现处全部**与数据面无关**：`packages/bench/src/payload/shell.ts:21,87`（W 层静态资源 gzip 字节预算，判定用 gzip、brotli 仅参考）、`relay-iac/lib/payload-init.sh:200`（Caddy `encode gzip` 静态站）、`.gitignore:46-47`（证据归档压缩，`*.jsonl.gz`，"压缩比实测 ~40×"）、`docs/field-acceptance/2026-09-17-l0-rum-first-measurement.md:94`（HTML gzip 后 0.87 KB 的观测）。

## ① 影响打洞成功率/直连率的手段与证据

### A. TURN 凭据只下发单 transport —— 三仓里唯一直接改变连通率的实测杠杆

**【实测】** v3net `docs/field-acceptance/2026-09-17-full-matrix-and-baseline.md:105-141`：实体机蜂窝三臂对照实验（n=6 × 3，唯一变量 = TURN transport）：

| 臂 | 配置 | 成功率 |
|---|---|---|
| A | UDP only（`?transport=udp`） | **6/6 = 100%** |
| B | TCP only（`?transport=tcp`） | **5/6 = 83%** |
| C | both（udp+tcp 同一下发，修复前生产配置） | **2/6 = 33%** |

原文结论（:113-116）："**不是 UDP 有问题，也不是多出口 NAT——而是同时下发两个 TURN URL（UDP + TCP）时，ICE agent 在两条 relay 路径间竞争，导致 TURN allocation 冲突与 15s 超时**。（若真是 UDP 被 NAT 破坏，臂 A 应当失败；实测臂 A 6/6 全过，假设被推翻。）"失败形态：SDP/ICE 交换正常但 `pc.state` 停在 `connecting`；coturn 侧记 `reason: allocation timeout` / `allocation watchdog determined stale session state`（:96-100）。

修复已落地（2026-09-17）：`v3net/supabase/functions/turn-credentials/index.ts:40-58` 默认只发 `?transport=udp`，TCP 走显式参数，注释全文记录实验。修复验证：both 2/6（33%）→ 单 UDP **5/6（83%）**（:129-134）；残留 1/6 归因为**蜂窝出口 IP 漂移**（coturn 侧观察到同一会话两个出口 IP `36.112.201.175` 与 `106.37.77.38`，中国电信多出口 NAT），定性为运营商侧行为，缓解手段 = ICE-restart 重试（:136-139）。

**跨仓警讯**：v2 仓的同名函数至今仍是双 transport 下发——`v2/devanywhere-website/supabase/functions/turn-credentials/index.ts` 返回 `turn:…?transport=udp` + `turn:…?transport=tcp` 两条 urls（该文件倒数第 12-8 行 `iceServers` 数组）。v2 已进维护模式，此修复未回填。**这给 v2 蜂窝 A/B 实验 B 变体 0/3 提供了一个事后候选解释【推断】**：B 变体（full ICE）用的正是 v2 双 transport 凭据。

### B. 首段 ICE 策略：STUN-only 分段级联 vs full ICE 合并 —— 蜂窝实测定夺

**【实测】** v2 `docs/superpowers/specs/2026-09-09-p0-ice-ab-decision.md:21-47`（Xiaomi + 中国联通 LTE、Wi-Fi 关、N=3×2）：

| 指标 | A（STUN-only 分段） | B（full ICE 合并，policy all） |
|---|---|---|
| 连通 | **3/3** | **0/3** |
| 成功路径 | **1/3 p2p 直连；2/3 经 TURN relay（50009/50019）** | — |
| 建连耗时 | 直连约 5s；TURN 路径约 15s（p2p 10s 超时 + TURN 5s 内） | full 15s 超时 + turn 兜底 15s 超时 |
| 观察 RTT | 39–109ms | — |

原始数据：`v2/devanywhere-client/pwa/dev/smoke-evidence/ice-ab-cellular/summary-a.json:43`（"A（显式分段 STUN-only + TURN-only）在本蜂窝环境 3/3 可用；p2p 直连 1/3，TURN 兜底 2/3"）、`summary-b.json:32`（B 0/3，"full 段之后的 turn-only 兜底段也 0/3（疑似 full 段失败后 daemon host 状态/时序未及时恢复）"）。

决策（:33-39）：保留显式级联分段（P2P 段仅 STUN + 10s 超时 → tunnel → TURN-only policy relay）；B 方案关闭，仅留 dev 钩子。**这是"级联分段"对"单 PC 全候选"的实测胜利，但样本仅 n=3、单运营商单手机。**

### C. STUN 服务配置：死节点教训与 fleet 化

- **【实测】死节点事实**：v2 生产 STUN 清单三节点里两台是死的——`v2/devanywhere-client/pwa/src/config.ts:26-30`（`stun:39.106.59.183 / 14.103.82.152 / 118.145.226.60:3478`），实验计划环境快照证实"relay-sh / relay-gz 只有 easytier 11010；**无 coturn**——现产 STUN 三节点里两台是死节点"（`v2/docs/superpowers/plans/2026-09-09-p0-ice-ab-cellular-android.md:36`）。决策文档把"死 STUN 节点是否移除（会影响直连成功率与 10s 超时内的候选质量）"列为待办（`2026-09-09-p0-ice-ab-decision.md:44`）。用自建 coturn 做 STUN 而不用谷歌公共 STUN 的理由写在 config.ts:25（"谷歌公共 STUN 在国内不可靠"）【文档推断】。
- **fleet 化（v3net）**：8 台 relay 全部 `roles: [turn, tunnel, static]`（`v3net/relay-iac/nodes.yaml:61,76,90,104,120,135,151`），coturn 全部 REST 短时凭证（`use-auth-secret`）+ `external-ip=公网/内网` 成对（`relay-iac/RUNBOOK.md:171,474`）。v3 浏览器端 STUN 默认值仍是同 3 台（`v3net/packages/browser/src/defaults.ts:35-38`）。
- **relay 端口段**：coturn `min/max-port=50000-50019`，每并发会话约 1 端口，生产按「并发 × ~1.2」估（`legacy/docs/coturn-relay-ops.md:55-57,216-218`）。
- **打洞相关配置坑（实测）**：云端 host 即兴 UDP 端口不在防火墙白名单 → srflx 不可达；绑定到放行段（`--ice-port-range 50000-50019`）恢复（`v3net/docs/benchmark/tc-cost-2026-09-15.md:200`）。**host 侧候选端口必须落在安全组放行段内，否则打洞必败。**

### D. 打洞的环境杀手：VPN/代理对 UDP 的破坏（全部【实测】，v3net T-C 系列实验）

- 现象：Mac 操作机 p2p 腿 **0/5**，host 侧 tcpdump 零入站检查（`tc-cost-2026-09-15.md:163-176`）。
- 机制钉死：VPN（utun6）使**单 socket 多目的地 UDP 被钉流到首个目标**或整体丢失；werift 恰好是单 socket 多目的地形态（同 socket 先发内网候选 `10.0.0.3:50000` 再发公网候选）（:178-194）。
- 判决性对照：同机 VPN off → 打洞 **0/5 → 5/5**（setup 5.7–7.2s、下行 9.97 MiB/s）（:215-221）；干净云机 peer 对照 **10/10 直连**（:207-213）。
- 不关 VPN 的四个绕过方案全部实测有效（`vpn-bypass-matrix-2026-09-16.md:24-30`）：`IP_BOUND_IF=en0`（Darwin）、绑定源地址、**每目标独立 socket**、host 路由例外；其中路由例外完成端到端验证"直连 5/5、下行 6.48 MiB/s"（:60-63）。

**迁移含义最大的工程事实**：ICE agent 的 socket 结构（单 socket 多目的地 vs 每目的地 socket）在带 VPN/代理的桌面环境里直接决定打洞成败。

### E. IPv6 直连 / UPnP / NAT 类型检测与引导 —— 只存在于 EasyTier 线

- **v2/v3 WebRTC 栈：三项全无**。v3net 全部 packages 里 IPv6 仅出现于 bridge 本机回环回退测试（`packages/node/tests/bridge.test.ts:391`）；UPnP 与 NAT 类型检测零命中（唯一例外是 bench README 把"NAT 类型"列为未来劣化注入项，`packages/bench/README.md:23`）。**T-D（严格 NAT/CGNAT 双命名空间仿真，测打洞率）至今是扩展位**——`packages/bench/src/topology.ts:92-99` 写明 runner 见到 T-D 要明确报错，装置（iptables MASQUERADE / 锥形与对称 NAT 规则）未建。
- **legacy EasyTier 线（机制存在，对 WebRTC 栈只能作假设来源）**：
  - NAT 类型检测：`cores/PeerToPeer/easytier/src/common/stun.rs:482-539`（OpenInternet/FullCone/PortRestricted/Symmetric/SymmetricEasyInc/SymmetricEasyDec 六类 + extra bind test）。
  - 用户侧引导：`cli/lib/doctor.js:108-134`——对称型提示"打洞大概率失败，走自建中继属于预期行为"，非对称提示"P2P 打洞成功率高"。
  - 杠杆清单【文档推断】：`docs/capacity-plan-100k.md:37`"提升打洞率（每 +10% 打洞率 ≈ 中继成本 -40%）：启用 IPv6 直连、UPnP、引导用户路由器配置"——**写了但没在该仓实测过这些手段对直连率的提升幅度**；产品代码（desktop/cli/mobile）未找到 IPv6 直连/UPnP 开关的实际使用。
  - EasyTier 的"先生中继、后台打洞、分钟级升级"【实测】：`docs/first-live-run-report.md:36`——Sym↔PortRestricted 组合给足时间后台打穿并自动升级 DIRECT（relay 424ms → p2p 551ms）；且"p2p 不一定更快"（:37）。

### F. ICE 候选优先级

三仓**均无**任何显式候选优先级操控代码（无 priority 调整、无 candidate 过滤策略）。实际机制是**级联分段**代替优先级：p2p 段只用 STUN 自收集（不含 TURN 候选，"直连失败不悄悄滑进 TURN"，`v3net/docs/architecture.md:88`），TURN 段 `policy=relay`"不做无谓打洞"（:90）。段超时即预算：v2 `CASCADE_TIMEOUT_MS = { p2p: 10s, tunnel: 6s, turn: 15s }`（`v2/.../config.ts:36`）。

## ② 信令成本随规模的形状

### "ws 信令长连是 10 万级才成立的账"——原文与数字

最完整表述在 `v3net/docs/signaling-longconn-design.md`（Stage 0.4 设计稿，2026-09-14，状态"待裁决"）：

- 现状（:11）：每端每 800ms 一次 PostgREST `poll(room, cursor)`，发送走 POST 同表。
- 量化（:15-20）：**轮询暗成本 = 1 万在线 3.3 万 QPS（plan-g 口径）；10 万在线 ≈ 12.5-33 万 QPS**；建链时延里"**T_dc_open 里 0.8-1.2s 是纯轮询等待**"（每跳白等 pollMs/2 = 400ms，一次建链 2-3 跳）；`signaling_qps_per_online ≤0.01` 在轮询制下"物理上不可达（轮询制 = 1.25-3.3）"；"Supabase Pro（$25/mo）的 PostgREST 计算量与 Realtime 并发配额都撑不到 1 万在线，遑论 10 万"。
- 结论原文（:22）："**轮询制不是「慢一点」，是在 10 万用户目标下直接不成立。这是 Stage 0.4 存在的理由。**"
- 三案成本账（:50-58）：现状轮询 = **不可行**；A 案 Supabase Realtime = 10 万并发 × $10/千 + 基础档 ≈ **$1000+（￥7000+）/mo，线性无杠杆**；B/C 案 relay 自建 ws = 10 台 4C8G ≈ **￥2000-4000/mo**（"边际成本是固定服务器租金（量级 ￥200-400/台/月），无 per-connection 抽成"）。
- plan-g 原始出处：`TryEverything/DevAnyWhere-v3/docs/proposals/plan-g-staged-evolution.html:217`"改造后信令成本 ≈ 单台 4C8G 可承载 1 万长连接，**月成本 < 500 元**"；:216 账单 >5 万元/月 = 门禁。
- **口径注意**：3.3 万 QPS 对应 **300ms** 轮询（plan-f/plan-g 原文"1 万在线 × 300ms 轮询 = 3.3 万 QPS"，`plan-f-measurement-first.html:242`），而 v2 实际实现默认 **pollMs=800ms**（`v2/cores/devanywhere-p2p/src/signaling/client.ts:16-17`）→ 即 1.25 QPS/在线。引用时按 1.25–3.3 QPS/在线的区间口径才稳。
- 附带论点【文档推断】：plan-b 称"轮询延迟本身就在毒害打洞成功率（offer/answer 晚 150ms，NAT 映射可能已老化）"（`plan-b-go-pion-sidecar.html:138`）——**无对照实验**。

### Supabase 限额：引用 vs 实测

- Realtime 定价只有**一处引用，且自我标注为量级估算**【文档推断】：`signaling-longconn-design.md:30`"公开定价量级为 Pro 含 ~500 并发、超出约 $10/千连接/月（以官网当期价为准，此处为量级估算）"。**三仓均未实测过 Realtime 并发连接数或消息量限额。**
- 唯一实测撞过的 Supabase 限额是 **Auth token 端点 429**【实测】：`v2/docs/handover-2026-09-09-mobile-pwa.md` §3.3——daemon 续期失败无退避，"800ms 轮询打令牌端点 → **429 永久限流**"；修复 = daemon 专用会话 + 60s 退避。与 Realtime/PostgREST 无关，但证明 Supabase 各面都有 rate limit 且会被客户端轮询行为打爆。

### ws 长连容量：已实测（v3net Stage 0.4 门禁）

- 门禁定义：`docs/stage-charter.md:43`——单机 4C8G **≥1 万并发长连接**；`signaling_qps_per_online ≤0.01`。
- 首测（2C/1.9G relay-sh，2026-09-14，`docs/benchmark/signaling-load-relay-sh-2026-09-14.md`）：累计开通 6k 无压力；投递时延含真实 PostgREST 双写 **p50 189–250ms、p95 237–621ms**（:97）；逼出设计级缺陷"心跳一拍即割（5s）在 WAN 拥塞下批量收割健康连接"（对照实验 100/100 → 失速后 100/100 被割，:107-113），修为 `deadAfterMs = 3×heartbeatMs = 15s`、任意入站帧刷新存活；修正后 1958 开通 → 1956 存活（99.9%）、timewait 3292→17（:170-173）。分布式 4 driver 网格把 2C 机顶到 **4113 并发真值**（:336-344）。
- 门禁机复测（4C/7G relay-sh2，2026-09-17，`signaling-10000-rerun-2026-09-17.md`）：**10000 并发 3/3 次全存活**（closedAfterOpen 0/0/1），healthz 连续四拍稳定 10000（:20-31）。
- QPS 读数：`signaling-gate-sh2-2026-09-14.md:17-18`——`signaling_qps_per_online ≈ 0.0099`（msgsReceived 11900 ÷ 万级在线 × 稳态窗，mailboxFailures=0），达成 ≤0.01 门禁【实测，但该值是发送方每秒 1 条消息的负载模型下的读数】。
- **成本形状结论**：信令帧 KB 级、仅建链期，长连后 QPS/在线 ≈ 0.01（事件驱动），10 万在线 = 10 台 4C8G 量级、成本与 relay 流量费合并计提——**从"随在线数线性增长的 per-request 云账单"变成"固定服务器租金"**。

| H1 | **TURN 凭据只下发单 transport（默认 UDP），TCP 走显式重试/级联**；同时下发 udp+tcp 会把 TURN 建链成功率从 ~100% 拉到 ~33% | 【实测】n=6×3 三臂对照 + 修复后复测（v3net，电信蜂窝 + werift/flutter_webrtc 两侧） | p2p-net 的 turn-credentials（或等价签发处）改为单 URL；客户端需有"UDP 失败 → ICE-restart/下一段换 TCP"的重试语义。若 p2p-net 当前也是双 transport 下发，这是**零成本最高收益**的一条 |
